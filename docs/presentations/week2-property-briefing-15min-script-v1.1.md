- **발표자:** 도시아재
- **과정:** GPTERS 23기 Codex 앱 스터디
- **예상 시간:** 15분
- **문서 버전:** v1.1
- **상태:** 2026-08-04 리허설 반영본
- **공개 범위:** 발표 대본과 승인된 비식별 수치만 공개 가능

> **핵심 메시지** 1주차에 만든 실용보드가 2주차의 Plan·Goal·Skill·Plugin·MCP를 만나, 실제 매물 한 건을 입력·대조·검수·승인·기록하는 업무 시스템으로 발전했습니다.

## 발표 원칙

- 부동산 전문지식보다 **Codex가 업무를 어떤 순서로 처리했는지**를 설명합니다.
- AI가 정답을 판단했다고 말하지 않고, **근거·충돌·미확인을 분리하고 사람이 승인했다**고 설명합니다.
- 실제 주소, 소유자·임차인정보, 계약서 원문, Drive·Sheet·Apps Script·비공개 URL은 보여주지 않습니다.
- 시연은 저장된 실제 파일럿을 불러오되, 화면 공유 전 개인정보가 있는 1단계를 지나 **2단계 대조 화면부터 보여줍니다.**
- 발표 중에는 비공개 DB 저장·공개 요약 전송 버튼을 누르지 않습니다.
- 실측값은 동일 사례 학습효과가 포함된 파일럿 한 건의 결과이며 일반화하지 않습니다.

## 2:30~4:00 | 기존 업무에서 무엇이 문제였나

**화면:** 비공개 앱의 5단계 흐름 또는 사례글 소개
**조작:** 세 가지 문제를 손가락으로 하나씩 세며 설명합니다.

제가 매도 의뢰를 받으면 매도희망가만 기록하는 것으로 끝나지 않습니다.

의뢰인이 알려준 보증금, 월세, 계약기간을 임대차계약 내용과 맞춰봐야 합니다. 등기사항전부증명서, 건축물대장, 토지이용계획과 실제 사용 현황도 비교해야 합니다.

여기서 세 가지 문제가 생깁니다.

첫 번째, 의뢰인의 설명과 계약 내용이 다를 수 있습니다.

두 번째, 공부서류의 용도나 면적과 실제 사용 현황이 다를 수 있습니다.

세 번째, 고객에게 설명할 내용과 공인중개사가 추가로 확인할 내용이 섞일 수 있습니다.

그래서 AI가 어떤 값이 맞는지 마음대로 결정하게 하지 않았습니다.

**서로 다른 값을 나란히 보여주고, 차이와 확인 필요 사항을 표시한 뒤 제가 최종 판단하도록 만들었습니다.**

## 4:00~5:30 | Plan·Goal·Skill·Plugin·MCP란 무엇인가

**화면:** Plan·Goal 증거 화면에서 비공개 앱 상단 5단계로 이동
**조작:** 기능명을 말할 때마다 쉬운 비유를 바로 붙입니다.

이번 주 수업의 핵심 기능을 쉬운 말로 설명해 보겠습니다.

**Plan 모드**는 일을 시작하기 전에 하는 설계 상담입니다. Codex가 바로 앱을 만들지 않고 기존 업무 순서, 자주 빠지는 정보, 결과물을 사용할 대상과 완료 기준을 먼저 질문했습니다.

**Goal**은 공사가 어디까지 끝나야 완성인지 적어놓은 완료 검사표입니다. 앱만 만드는 것이 아니라 실제 사례 한 건, 사람 승인, 시간과 수정 횟수, 비식별 결과 저장까지 완료 조건으로 정했습니다.

**Skill**은 우리 사무실의 업무 매뉴얼입니다. 자료 우선순위, 충돌 처리, 고객용 문구와 내부 검수 분리 규칙을 다음 매물에도 다시 사용할 수 있게 했습니다.

**Plugin**은 Google Drive 같은 외부 서비스로 들어가는 연결문입니다.

**MCP**는 건축물대장이나 실거래처럼 외부의 최신 자료를 조회하는 공식 창구라고 이해하면 쉽습니다.

그리고 **Codex는 이 도구들을 업무 순서에 맞게 움직이는 실무 진행자** 역할을 했습니다.

# 시연

## 5:30~6:00 | 전체 업무 단계

**화면:** 보호된 비공개 앱 상단
**조작:** 5단계를 가리킨 뒤 저장본 불러오기 전환을 설명합니다.

이 앱에는 다섯 단계가 있습니다.

입력과 마스킹, 공적 자료 대조, 임대차 검수, 고객용·내부용 결과 분리, 마지막으로 사람 승인과 기록입니다.

공인중개사가 처리하는 순서를 화면에 옮긴 것입니다.

오늘은 저장된 실제 파일럿을 불러오지만, 개인정보가 있는 입력 화면은 공유하지 않고 검증 구조와 승인된 비식별 결과만 보여드리겠습니다.

## 6:00~7:40 | 저장된 실제 파일럿과 공적 자료 대조

**화면:** 1단계에서 저장본을 불러온 뒤 바로 `공적 자료·설명값 대조`로 이동
**조작:** 사전 준비한 케이스 ID를 입력하고 `저장본 불러오기`를 누릅니다. `실제 사건 모드`로 불러와진 것을 확인하되 주소·가격은 노출하지 않고 2단계로 스크롤합니다.

시연 순서는 먼저 케이스 ID를 입력하고 저장본 불러오기를 누르는 것입니다.

저장된 파일럿을 불러오면 실제 사건 모드가 됩니다. 이 동작은 저장된 데이터를 읽어오는 것이며, 그 자체로 DB를 수정하거나 공개하지 않습니다.

여기서는 원문 값과 최신 조회값, 기준일과 확인일, 차이와 대표님 판단을 나란히 남깁니다.

두 값이 다르다고 해서 하나를 지우거나 최신값으로 덮어쓰지 않습니다.

이번 파일럿에서는 건축물대장 표제부의 지상층수와 층별개요에서 확인되는 6층이 다르게 보였습니다.

또 1층의 현재 사무실 사용과 공부상 소매점·옥내주차장 용도가 달랐습니다.

Codex가 어느 것이 정답이라고 결정한 것이 아니라 불일치로 표시했고, 제가 실제 층의 존재와 면적, 1층 임대범위를 확인해 판단 내용을 기록했습니다.

**AI가 답을 대신 결정하는 것이 아니라 사람이 확인해야 할 지점을 찾아주는 것**이 이번 자동화의 핵심입니다.

## 7:40~8:40 | 임대차 대조

**화면:** `임대차 검수`
**조작:** 계약 4건과 보증금·월세 합계까지만 보여줍니다.

임대차계약 4건의 내용을 같은 항목으로 정리했습니다.

각 계약의 층, 보증금, 월세, 만기와 확인 상태를 한 화면에서 비교할 수 있게 했습니다.

합계뿐 아니라 계약 원본 확인 여부와 계열사 임대료처럼 시장 임대료의 대표성을 사람이 판단해야 하는 항목도 남겼습니다.

다만 이번 첫 파일럿에서는 Google Drive의 계약서 PDF를 Codex가 직접 판독하지 않았습니다.

제가 계약서 원본을 확인해 제공한 전사값을 사용했고, **마스킹된 PDF 직접 판독은 다음 실험으로 남겼습니다.**

## 8:40~9:40 | 고객용 결과와 내부 검수 분리

**화면:** `고객용 결과와 내부 검수 분리`
**조작:** 왼쪽 고객용 제안서와 오른쪽 내부 검수표의 제목과 역할만 가리킵니다.

왼쪽은 고객에게 보여줄 매수 목적별 제안서입니다. 확인된 매물 개요, 임대현황, 입지 근거와 가격 검토 요인을 담았습니다.

오른쪽은 공인중개사 내부 검수표입니다. 공부서류 간 충돌, 계약서 원본 확인, 공부상 용도와 실제 사용의 차이처럼 사람이 먼저 판단해야 하는 내용을 따로 기록했습니다.

AI가 글을 얼마나 많이 써주는가보다, **고객에게 말해도 되는 내용과 사람이 끝까지 확인해야 할 내용을 분리하는 것**이 더 중요했습니다.

## 9:40~10:30 | 3단계 승인과 공개 결과

**화면:** `승인·기록`에서 공개 실용보드 Week 2 결과로 이동
**조작:** 승인 3개와 Before/After를 가리키되 저장·공개 버튼은 누르지 않습니다.

AI가 초안을 만들었다고 바로 저장하거나 공개하지 않습니다.

첫 번째는 입력자료와 비식별 처리 승인입니다.

두 번째는 공적 자료와 임대차 교차검증 승인입니다.

세 번째는 고객용 제안서와 내부 검수표 분리 승인입니다.

이 세 단계를 제가 직접 확인한 뒤 비공개 DB에 저장했습니다.

공개 보드에는 실제 주소나 계약내용을 보내지 않았습니다. 승인된 활동시간, 근거 수, 충돌 수, 미확인 수, 수정 횟수와 배운 점만 전송했습니다.

# 예상 질문과 답변

## 비식별 자료와 비식별 결과는 무슨 뜻인가요?

자동차 사진을 공유하기 전에 번호판을 가리는 것과 비슷합니다. 이름·연락처·계약서 원문처럼 개인을 알아볼 정보는 가리고, 업무 검증에 필요한 자료 종류·차이·상태·처리 구조만 남긴 마스킹 자료입니다.

## 실제 사건 모드인데 왜 비식별 시연이라고 하나요?

저장된 실제 파일럿을 읽기 때문에 앱에서는 실제 사건 모드입니다. 그러나 발표 화면에서는 주소·가격·원문 링크가 있는 입력 단계를 보여주지 않고, 공개 보드에는 승인된 통계와 배운 점만 전송했습니다. 실제 입력과 공개 결과를 구조적으로 분리했습니다.

## 근거 13건과 임대차 4건은 겹치나요?

측정 대상이 다릅니다. 임대차 4건은 계약별 금액·기간을 관리한 레코드입니다. 근거 13건에는 공적 자료뿐 아니라 임대차 내용을 등기·건축물대장과 대조한 4개의 교차검증 행도 포함됩니다. 하나는 계약 수, 다른 하나는 검증 근거 행 수입니다.

## 충돌 2건과 미확인 4건은 중복인가요?

중복이 아닙니다. 충돌은 상태가 `불일치`인 2건입니다. 미확인은 `기준일 경과·자료 없음·추가 확인 필요·판독 불가`를 합친 4건입니다.

## AI가 권리 안전성이나 적법성을 판단했나요?

아닙니다. Codex는 자료를 정리하고 충돌과 확인 필요 항목을 표시했습니다. 계약서 원본 확인과 고객에게 전달할 표현의 최종 승인은 공인중개사가 담당했습니다.

## Plugin과 MCP를 모두 완성해서 사용했나요?

매물 브리핑 Skill과 건축물대장·실거래 MCP 조회는 실제 흐름에 적용했습니다. Google Drive Plugin은 마스킹 입력 경로로 설계했지만 계약서 PDF 직접 판독은 다음 실험으로 남았습니다. 서울시 공식 웹 자료도 계획 단계 확인에 사용했습니다.

## 1,140분이 24분으로 줄었다고 일반화할 수 있나요?

일반화할 수 없습니다. 동일 사례를 다시 처리한 학습효과가 포함되어 있습니다. 이번 파일럿 한 건의 활동시간으로만 기록하고, 처음 보는 두 번째 매물에서 같은 기준으로 재측정할 예정입니다.

## 13건 중 확인됨인 자료도 고객에게 그대로 말해도 되나요?

아닙니다. `확인됨`은 해당 자료의 조회와 대조 상태입니다. 계획 자료는 계획 단계로 표현하고, 개별 매물의 가치상승·권리 안전성·수익을 보장하는 문장으로 바꾸지 않습니다.

## 다른 매물에도 바로 사용할 수 있나요?

업무 절차와 검수 규칙은 Skill로 재사용할 수 있습니다. 다만 실제 재사용성을 확인하려면 처음 보는 두 번째 매물과 계약서 PDF 직접 입력 실험이 필요합니다.

## 왜 고객용과 내부용을 나눴나요?

고객용에는 확인된 사실과 조건부 설명만 담고, 공부서류 충돌·계약서 원본 확인·시장 대표성처럼 공인중개사가 먼저 판단할 항목은 내부 검수표에 남기기 위해서입니다.

## 앱이 자동으로 저장하고 공개하나요?

아닙니다. 대표님이 3단계 승인 후 비공개 DB 저장과 공개 요약 전송을 각각 실행했습니다. 발표 중에는 저장·공개 버튼을 누르지 않습니다.
